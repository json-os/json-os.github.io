How It Works

Understanding jsonos examples for SolidOS developers

The Big Picture

These examples use the exact same stack as SolidOS, just with JSON-LD data embedded in the page instead of fetched from a pod.

┌─────────────────────────────────────────────────────────────┐ │ person.html │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ <script type="application/ld+json"> │ │ │ │ { "@type": "schema:Person", "schema:name": "..." } │ │ │ │ </script> ← JSON-LD data │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ Parse into store │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ mashlib.min.js (solid-shim) ← Same as SolidOS │ │ │ │ ├── rdflib → $rdf, store │ │ │ │ ├── solid-ui → UI widgets │ │ │ │ ├── solid-logic → SolidLogic.store │ │ │ │ └── solid-panes → Pane system │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ src/panes/person.js ← Custom pane │ │ │ │ Reads from store, renders UI │ │ │ └───────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘
Key insight: The panes work identically to SolidOS panes. They read from SolidLogic.store using $rdf - the only difference is where the data came from (embedded JSON-LD vs fetched Turtle).

What's mashlib.min.js?

It's solid-shim - a mashlib-compatible bundle built from JSS forks:

ComponentWhat it doesSolidOS equivalent
rdflibRDF parsing, store, fetcherSame
solid-ui-jssUI widgetssolid-ui
solid-logic-jssBusiness logic, authsolid-logic
solid-panes-jssPane systemsolid-panes
solid-oidcAuthenticationsolid-authn-client

The only real difference: solid-oidc replaces solid-authn-client for auth.

How Data Flows

1. JSON-LD Data Island

Each page has embedded JSON-LD (this is standard HTML, works in any browser):

<script type="application/ld+json">
{
  "@context": { "schema": "http://schema.org/" },
  "@id": "#me",
  "@type": "schema:Person",
  "schema:name": "Marie Curie"
}
</script>

2. Parse into RDF Store

On page load, we parse the JSON-LD into the same SolidLogic.store that SolidOS uses:

// This is what shared.js does internally
const store = SolidLogic.store;
const subject = $rdf.sym(baseUri + '#me');

// Add triples to store
store.add(subject, RDF('type'), $rdf.sym('http://schema.org/Person'));
store.add(subject, SCHEMA('name'), 'Marie Curie');

3. Pane Reads from Store

The pane reads data exactly like a SolidOS pane would:

// src/panes/person.js - same pattern as SolidOS panes
const SCHEMA = $rdf.Namespace('http://schema.org/');

const name = store.anyValue(subject, SCHEMA('name'));
const image = store.any(subject, SCHEMA('image'));
const jobTitle = store.anyValue(subject, SCHEMA('jobTitle'));
This is the same API you'd use in a SolidOS pane. The pane doesn't know or care that the data came from a JSON-LD island instead of a fetched Turtle file.

shared.js - The Glue

src/shared.js is the bridge between JSON-LD data islands and SolidOS panes. It eliminates ~160 lines of boilerplate per page.

The JSON-LD Parser

The key function in shared.js converts JSON-LD to RDF triples:

// Simplified from shared.js
function addTriples(node, subjectUri) {
  const subject = $rdf.sym(subjectUri);

  // Add type triple
  if (node['@type']) {
    store.add(subject, RDF('type'), $rdf.sym(node['@type']));
  }

  // Add property triples
  Object.keys(node).forEach(key => {
    if (key.startsWith('@')) return;  // Skip @context, @id, @type

    const predicate = $rdf.sym(key);  // e.g., schema:name
    const value = node[key];

    if (value['@id']) {
      store.add(subject, predicate, $rdf.sym(value['@id']));  // Link
    } else {
      store.add(subject, predicate, value);  // Literal
    }
  });
}

After this runs, the store contains the same triples you'd get from fetching Turtle from a pod.

Backwards Compatibility

Existing panes export to window.SchemaPersonPane, etc. shared.js detects these automatically:

// shared.js detects existing panes by convention
// 'src/panes/person.js' → looks for window.SchemaPersonPane
const globalName = 'Schema' + 'Person' + 'Pane';
if (window[globalName]) {
  paneRenderer = window[globalName].render;
}

This means existing panes work without modification.

Usage

With shared.js, a complete example is just:

<script type="application/ld+json">
{ "@type": "schema:Person", "schema:name": "Marie Curie", ... }
</script>

<script src="src/shared.js"></script>
<script>
  SchemaShared.init({
    pane: 'src/panes/person.js',
    subject: '#me'
  });
</script>

That's it. ~40 lines instead of ~230.

Pane Compatibility

The custom panes in src/panes/ follow the same pattern as SolidOS panes:

FeatureHow it works
Read datastore.anyValue(subject, predicate)
Get linksstore.any(subject, predicate)
Query triplesstore.statementsMatching(s, p, o)
Namespaces$rdf.Namespace('http://schema.org/')
Symbols$rdf.sym('http://...')

If you can write a SolidOS pane, you can write these panes. Same API.

Why JSON-LD Data Islands?

  • Zero server - Works on static hosting (GitHub Pages)
  • SEO friendly - Search engines understand JSON-LD
  • Portable - Copy the HTML file, it just works
  • Familiar - Same as schema.org structured data

The Goal

Show that SolidOS patterns work with any RDF data source:

  • Solid pods (Turtle, fetched)
  • JSON-LD islands (embedded)
  • Any RDF endpoint

The panes don't care. They just read from the store.
